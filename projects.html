FloodLink — Real-Time River Monitoring & Flood Prediction System

Role: Project Team Member · Department of Electrical & Electronic Engineering, UoP

A low-cost, LoRa-based, real-time river-monitoring and flood-prediction system built to give vulnerable communities earlier warnings — winner of 2nd Place at Idea to Invention 2025.

Sri Lanka faces recurring flash floods and seasonal droughts that hit vulnerable communities hardest and cost lives. The information that would help — how fast a river is actually rising, right now — usually does not exist until the water is already in the street. FloodLink was built to close that gap: a low-cost river-monitoring and flood-prediction system that communities and authorities can act on early.

Key Highlights

Real-time river-level monitoring
ML-based time-to-threshold flood prediction
Long-range, low-power LoRa communication
Telegram alerts + local siren warnings
Works reliably even during internet outages
Supports both flood and drought monitoring

Team

Olitha Induvara Yeshini Illagolla Sithum Sathsara Nanduni Rathnayake
LoRa ESP32 Ultrasonic Sensors Machine Learning Telegram Alerts Flood Early Warning GUI Dashboard

The Sensor Node

Each monitoring point is a waterproof ultrasonic sensor node mounted above the river, measuring the distance down to the water surface and turning that into a live level reading. The nodes are solar-powered and built to sit outdoors unattended, which is the only way a river network of this kind can be affordable to run.

LoRa — Range Without Infrastructure

Riverbanks are exactly the places where mobile coverage is worst, so the nodes talk over a long-range LoRa network instead of relying on the internet. Readings travel kilometres on very little power and reach a central receiver directly, which means the system keeps reporting during the storms and outages when it matters most — the failure mode that defeats most connected sensors.

Predicting the Rise, Not Just Reporting It

A level reading on its own still only tells you where the water is. FloodLink’s machine-learning models take the trend and predict the time remaining before Alert, Minor and Major flood levels are reached, which turns a measurement into a decision: how long is there to move, and is it enough. Warnings go out through Telegram and a local siren, so a community without smartphones is still reached.

The same data works in the other direction too — sustained low levels make the system useful for drought monitoring as well as floods.

sEMG-Based Prosthetic Hand Control System

My role: Analog Front-End Design & Acquisition Software · Department of Electrical & Electronic Engineering, UoP

A wearable surface-electromyography (sEMG) system that reads the electrical activity of forearm muscles and decodes it into hand gestures — intended as a natural control interface for prosthetic hands, robotics and assistive devices. My responsibility in Semester 1 was the analog front-end that captures the muscle signal, together with the software used to record and visualise it.

When a muscle contracts it produces a small electrical signal that can be picked up by electrodes on the skin. Those signals are only a few millivolts, they sit in a narrow frequency band, and they arrive buried in mains hum and movement artefacts. Turning that into something a computer can classify as a gesture is the core engineering problem — and it begins long before any machine learning, because the signal has to be acquired cleanly in the first place.

That acquisition chain was my part of the project. Over the semester I designed, built and tested three successive versions of the analog front-end (AFE), each one answering the problems the previous version exposed, and I developed the standalone recording software the team used to capture and inspect the data. The group’s wider work covered the gesture-recognition pipeline and a reproducible electrode-placement framework, supervised by Dr. Ruwan Ranaweera, Dr. Nalin Harischandra and Prof. Vajira Weerasinghe.

What I Delivered

Battery-powered dual-rail supply, no mains connection

Validated on real muscle signals during hand gestures

Acquisition & Visualisation Software

The first obstacle was not hardware at all. There was no suitable software for recording, visualising and filtering EMG signals from the NI DAQ cards available to us — the usual route means writing fresh MATLAB or Python code for every session. So I built my own application and packaged it as a standalone executable, which means any EMG researcher can download and run it through a proper interface without installing Python or any libraries. It records three channels in real time, shows live traces and RMS muscle-activity levels, applies a built-in 50 Hz notch filter to strip power-line noise, and saves the captured data for later analysis.

Version 1 — Learning the Signal

The first prototype was deliberately simple: a hand-soldered dot board built around a basic quad op-amp, with no instrumentation amplifier, no driven-reference stage and only minimal filtering. It was never meant to be the final circuit. I built it to get familiar with what a real EMG signal looks like and, just as importantly, to find out exactly where the noise comes from. Muscle activity was visible — but the mains interference it picked up made the limits of this approach obvious, and set the agenda for the next version.

Version 2 — Precision and Noise Rejection

Version 2 was a substantial upgrade, built directly on what Version 1 revealed. I moved to a precision AD620 instrumentation amplifier for the input stage, paired with a TL074 op-amp for the filtering and gain stages, which gave far better rejection of interference common to both electrodes. The important addition was a driven-reference (DRL) stage — in simple terms, it feeds the interference back to the body through the reference electrode, so power-line noise is cancelled at the source instead of being filtered out afterwards. The improvement in signal quality was immediate.

Version 3 — Two Channels on a Fabricated PCB

With the Version 2 architecture proven, Version 3 took it to a two-channel design laid out properly in KiCad and manufactured as a real PCB rather than hand-wired on perfboard. This is the version that validated the whole approach: with electrodes on the forearm I was able to capture and clearly distinguish two different muscle signals during hand gestures — exactly the multi-channel behaviour the gesture-recognition side of the project depends on.

Power Supply — A Deliberate Safety Decision

The Version 3 board needs a dual supply, both a positive and a negative rail, because an EMG signal swings either side of zero. I designed a custom power module for it, and made one decision very deliberately: no AC wall supply. Mains power is a safety concern for anyone wearing electrodes on their skin, and it is also the single largest source of the 50 Hz noise the whole front-end is fighting. Instead the module runs from a 12 V battery pack and generates both rails from it, which keeps the circuit electrically isolated from the mains and makes the system genuinely portable.

All Three Versions

Three boards in one semester — each built to answer a question the previous one raised.

SkyAQ — Real-Time Air Quality Measurement Drone

Hexacopter drone · ESP32 · Designed for EngEx 2025

A hexacopter that carries an air-quality payload into places people should not go — measuring particulates, humidity and temperature in real time and mapping the result as it flies.

Air quality is usually measured at fixed ground stations, which tells you about the handful of points somebody could safely install a box. SkyAQ lifts the sensors instead: a hexacopter carrying its own instrumentation, able to sample above a landfill, an industrial site or anywhere a person should not be standing — and to do it across an area rather than at a single point.

Key Highlights

ESP32-based hexacopter platform
PM2.5, DHT22, GPS & SD-card integration
Real-time environmental data logging
DJI NAZA flight control
Python GUI for live data visualisation
Safe monitoring of hazardous / inaccessible areas

Team

Olitha Induvara Tanusha Manuranga Damindu Gamage Madhuka Lakshan
ESP32 Hexacopter PM2.5 Sensor DHT22 GPS Air Quality Environmental Monitoring EngEx 2025

The Airframe & Payload

The aircraft is a hexacopter flying on DJI NAZA flight control, with six rotors chosen over four for the lift margin and the tolerance to lose a motor while carrying an instrument payload. That payload is built around an ESP32: a PM2.5 particulate sensor, a DHT22 for humidity and temperature, a GPS module so every sample knows where it was taken, and an SD card so nothing is lost if the link drops. The whole thing runs from a Li-Po pack.

Turning Flights Into Maps

Because every reading carries a GPS position, a flight produces more than a log file — it produces a picture. A Python GUI shows the data live as it arrives, and the recorded samples are plotted against the map and rendered as 3D particulate-density views, so a pollution gradient across a site becomes something you can actually see rather than a column of numbers.

FlyMe — Autonomous RC Plane & Ground Station

Role: Airframe, avionics, firmware and Android app · Solo project, ongoing

A long-running build working towards an RC plane that can fly autonomous waypoint missions for aerial photogrammetry and survey work. The aircraft flies today under manual control, carrying a GPS and IMU payload that streams live telemetry over LoRa to FlyMe, an Android ground station I designed and built to track and instrument the flight.

The goal behind FlyMe is to stop hand-flying survey patterns. A plane that can be given a set of waypoints and fly them accurately becomes a platform for photogrammetry — mapping, 3D reconstruction, site surveys — and for the aerial work I already do by drone, but over far larger areas than a multirotor can cover on one battery.

Getting there means solving each layer in turn, and this is where the project currently stands: a flying airframe, a working long-range telemetry downlink, and a ground-station app that visualises everything the aircraft knows about itself. Control surfaces driven by the flight computer, and then waypoint navigation, come next.

Where It Stands Today

KT-board airframe assembled and flight-tested
FlySky FS-i6 radio, 1200 mAh 3S LiPo
GPS + IMU payload streaming over 433 MHz LoRa
ESP32-C3 plane transmitter and ground receiver
FlyMe Android ground station with live map HUD
Flight recording, replay and GPX export
ESP32-C3 LoRa SX1278 MPU6500 IMU u-blox GPS Sensor Fusion Android USB-OTG Serial KiCad PCB Design Arduino / C++ Photogrammetry

The Aircraft

The airframe is a fabricated KT-board kit that I assembled myself — light, cheap to repair, and forgiving enough to carry an experimental payload without much worry about what a hard landing costs. It flies on a FlySky FS-i6 transmitter and receiver with a 1200 mAh 3S LiPo, which is enough for the test flights the project needs at this stage.

Flying it manually is not the point — but it is the prerequisite. Every automated behaviour planned for later has to be trialled against a known-good manual baseline first, and the flights so far have been about proving the airframe is stable and predictable enough to hand over to a computer.

Telemetry — LoRa from the Plane to a Phone

The aircraft carries an ESP32-C3 with a GPS module and an IMU. The IMU runs an attitude filter at 200 Hz to produce roll, pitch and heading, while the GPS supplies position, altitude and ground speed. Those are packed into a compact binary frame and transmitted ten times a second over 433 MHz LoRa — chosen over WiFi or Bluetooth because the range needed for survey flights is measured in kilometres, not metres.

On the ground a second ESP32-C3 receives those packets, unpacks them, and re-emits them as JSON. The phone connects to that receiver over a USB-C cable (WiFi is also supported), so the whole ground station is a phone and a small board in your hand — no laptop at the field. The link is bidirectional: the app can send calibration commands back up to the plane and watch them complete.

I built the plane and receiver electronics on perfboard first, then drew both as proper PCBs in KiCad for the next revision.

FlyMe — The Android Ground Station

This is the part I have put the most design work into. FlyMe is an Android app that turns the telemetry stream into something you can actually fly with: a full-screen HUD over a live satellite map showing the plane’s position and trail, distance from home, altitude above the launch point, ground speed and heading, with a compass and a return-to-home arrow.

Beyond the HUD it handles the things that matter when the aircraft is a dot in the sky — a home point taken from the phone’s GPS or dropped on the map, range rings, an attitude instrument driven by the IMU, a telemetry page with an altitude chart and signal quality, and spoken and vibrating alerts for signal loss, low altitude, low battery or exceeding maximum distance. If the link drops, the app holds and shows the last known position. Every flight is recorded automatically from take-off to landing, can be replayed with a scrubber, and exports as GPX.

Bring-Up — When the Parts Are Not What the Label Says

Two components turned out to be something other than what was sold, and both were only caught by interrogating the chips directly rather than trusting the listing.

The module advertised as a 9-axis MPU9250 returned WHO_AM_I = 0x70 — the signature of an MPU6500, which is 6-axis and has no magnetometer. Three independent bus probes confirmed nothing was on the magnetometer address. That matters more than it sounds: gravity gives an absolute reference for roll and pitch, so those hold steady indefinitely, but without a magnetometer there is no absolute heading. Yaw can only be integrated from the gyro, so it drifts a few degrees per minute. The app is honest about this and marks the heading as relative rather than pretending it is a true compass bearing.

Similarly, the GPS sold as a NEO-M8N answered a version poll as a relabelled NEO-6M. It gets a fix and works, but it tracks GPS satellites only. Knowing which part is actually fitted changed how the firmware is configured — it now sets an airborne dynamic model, rejects 2D fixes and low-elevation satellites, and only accepts a home point once the fix is genuinely good and the aircraft has been stationary for ten seconds.

What Comes Next

The immediate next step is a magnetometer on the same I²C bus to give a true heading rather than a drifting one — navigation is not possible without it. After that come servo and ESC outputs driven by the flight computer, so the aircraft can hold a heading and altitude on its own, and then waypoint missions: upload a route from the app, let the plane fly it, and bring it home. Once that is reliable, the camera payload and the photogrammetry work the whole project was started for can begin.

Quiz Buzzer System — FinFit Expo 2026

My role: Hardware design, electronics & soldering · With Sithum Sathsara · University of Peradeniya

A three-team quiz buzzer system designed and built for the quiz competition at FinFit Expo 2026, organised by the Central Bank of Sri Lanka at the University of Peradeniya — and used live on stage at the Arts Theatre.

A quiz only works if the buzzer is beyond argument. Whoever presses first has to be the one the system locks in, every time, with no ambiguity for the audience or the quizmaster — and on a stage in front of a full theatre there is no second attempt if something misbehaves. That is the whole brief, and it is a harder one than it sounds.

Who Built What

Olitha Induvara me Hardware & electronics

Circuit design, the controller electronics and all of the soldering — the lock-out logic, buzzer drive and the RJ45 wiring to each team pad.

Sithum Sathsara 3D design, laser cutting & assembly

Designed the enclosures in 3D, laser-cut the plates, and did the final assembly — which is why the finished kit looks as clean as it does. Also worked on the hardware.

Key Features

Three team stations, first-press lock-out
Plug and play — no setup or pairing
RJ45 Ethernet cabling to every buzzer
Audible buzzer and clear team indication
Single reset button on the controller lid
Laser-cut enclosures for stage-ready presentation

The Kit

The whole system is one controller box and three team pads. The controller carries a large reset button on the lid, a sounder behind the grille, and a row of sockets on the back for the teams. Each pad is a single large button on a laser-cut plate, weighted enough to stay put when somebody hits it hard. It is completely plug and play — connect the three cables, power it up, and it is ready for the first question. There is nothing to configure and nothing to pair.

Ethernet Cable as the Backbone

Every buzzer connects to the controller through an ordinary Ethernet cable, into RJ45 sockets on the back marked TEAM 1, TEAM 2 and TEAM 3. That one decision solved most of the practical problems at once. The cable is cheap and available anywhere, it comes in long runs so teams can sit well apart across a wide stage, and the connector clicks in and will not pull out mid-round. It also carries far more conductors than a single button needs, which left headroom for each pad’s indicator and for more teams later — and it means a damaged lead is replaced with any patch cable to hand, not a custom part.

Inside the Case

The controller electronics sit inside the laser-cut enclosure with the cabling dressed back to the RJ45 sockets, so the lid can come off for service without unpicking the loom. The lock-out logic is the heart of it: the first press latches that team, locks the other two out electrically rather than in software timing, drives the sounder and lights the indication — and holds that state until the reset button is pressed for the next question.

On the Night

The system ran the quiz competition at the Arts Theatre, University of Peradeniya, as part of FinFit Expo 2026. Building something that has to work first time, in front of an audience, with no chance to debug it between rounds, is a different discipline from building something for a bench — and it did its job.

RT Flow Watch — Smart Flow Meter for Sri Lankan Homes

My role: Hardware design & mobile application · Team project · Built to National Water Board requirements

Every drop counts. A complete smart-water system: a solar-powered meter for the home, a mobile app for households and Water Board staff, and a web dashboard for the utility — turning a once-a-month meter reading into live, accurate information.

The Problem

In most Sri Lankan homes water use is only seen once a month, when the meter reader visits. By then a hidden leak or a running tank has already wasted thousands of litres, the bill is a surprise, and the utility has no way of knowing which meters need attention. There is no picture of the network between one reading and the next.

The Solution

A meter that measures every litre, watches for leaks around the clock and reports by itself. It feeds an app that shows households exactly where their water and money go, and a dashboard that gives the Water Board a live view of every meter it manages. We built the whole chain — device, app and platform — against the Water Board’s own technical requirements, so this is a prototype aimed at deployment rather than a demonstration piece.

Who Built What

My side was the hardware and the mobile application — the meter electronics, firmware and enclosure, and the two-mode Android app for households and field staff. Chiran Tharushka led the concept and built the web platform. Yeshini Illagolla and Himasi completed the team.

The Device

RT Flow Watch measures flow continuously and keeps the meter reading, today’s use and the month’s use, rolling the monthly counter over automatically on the 1st. It holds months of history in its own memory so a network outage costs nothing, keeps its own clock, and reports to the Water Board every hour — but sends alarms immediately rather than waiting for the next report. It also watches itself, reporting faults in the clock, memory, display, network, battery or sensor, each with a suggested action. Customers cannot alter it; a protected service mode opens only at the meter, for authorised staff.

Building It

The electronics started on a breadboard to prove the sensing and the radio, moved onto hand-soldered perfboard as the design settled, and were then packaged with the flow sensor, battery and solar input into a weatherproof enclosure for outdoor life.

The Mobile App

One app, two modes chosen at start-up. Customer mode signs in with the meter ID and a personal PIN and is deliberately view-only: a seven-day consumption ring, today against yesterday, usage analytics by day, week, month and year, and a monthly bill estimated on the official Water Board tariff with the block-by-block breakdown, service charge and VAT. Paying opens the Water Board’s own payment page with the account number and amount already filled in. Leak, burst and high-use alerts arrive with advice on what to check.

Water Board mode ties a staff sign-in to one registered phone and limits access to that technician’s own area. It lists meters with alarms, faults and anything that has stopped reporting, and opens a full profile per meter. The part I am most pleased with is the guided service visit: an animated radar finds the meter over Bluetooth, then the technician presses the button on the meter itself while matching a code shown on both screens, and the server confirms the staff account. All three have to agree — so a meter cannot be altered remotely, or by someone who is not physically standing at it. Once in, the console offers a live flow gauge, health checks, a bucket-test calibration wizard, clock sync, self-test, alarm clearing and a log download.

Surviving the Real World

A meter bolted to a wall outside somebody’s house has to keep counting through everything: a flat battery, no signal, a dropped connection halfway through a report. Most of the engineering that is not visible in a screenshot went into what happens when something fails — because a meter that loses water data is worse than no meter at all.

Power & battery

  • Solar panel charging a rechargeable lithium cell — no mains connection
  • Battery voltage measured and reported with every health check (4.15 V on the unit shown)
  • Battery is one of the six monitored subsystems, each fault carrying a suggested action
  • A low battery is raised to the Water Board as a fault, so a unit is serviced before it goes dark
  • Metering continues while the radio is the first thing to go quiet

Mobile network (2G / GSM)

  • GSM cellular modem — 2G chosen for coverage and power, not speed
  • Telemetry is a few hundred bytes an hour, so 2G is the right fit
  • Signal strength reported on the standard 0–31 scale (16/31 on the unit shown)
  • Scheduled report every hour; alarms break the schedule and go immediately
  • Mobile network is a monitored subsystem; loss of signal is itself a reportable fault
  • A failed report is not discarded — it stays queued in memory

Memory & store-and-forward

  • 4,072 records of on-board storage — roughly 170 days of hourly history
  • Every reading is written to memory first, then sent
  • An outage costs no data: the meter keeps logging regardless
  • A “not yet on the server” counter tracks the unsent backlog
  • When the network returns, the backlog is uploaded until the counter clears
  • Memory health is checked continuously and a module failure is reported as an error

Timekeeping

  • The meter keeps its own time independently of the network
  • Clock corrects itself automatically once a connection is available
  • Accurate timestamps are what make night-leak detection and the monthly rollover possible
  • Without a trustworthy clock a stored backlog would be meaningless, so the clock is a monitored subsystem in its own right
  • A technician can force a clock sync from the service console at the meter

Self-recovery

  • Restart count kept and reported, so repeated resets are visible to the utility
  • Six subsystems monitored: clock, memory, display, mobile network, battery and flow sensor
  • Each reported fault names a recommended action rather than just a code
  • Faults reach the Water Board dashboard and the staff app, not just the on-device screen
  • The full meter log can be pulled to the server during a service visit

How It Works

The bottle sits on a coaster containing a weight sensor that monitors the water level continuously. Real-Time Sobel Edge Detection on an FPGA

Role: Sole developer · Semester 6 individual project · Department of Electrical & Electronic Engineering, UoP

An edge-detection engine built as digital hardware rather than software — a Sobel filter written in Verilog, verified pixel-by-pixel against a Python/OpenCV reference, then synthesised onto a Basys3 FPGA where it filters an image and drives a VGA monitor live, with no processor running anywhere in the system.

What a Sobel Filter Actually Does

An edge in a photograph is simply a place where brightness changes sharply — the boundary between a car’s bodywork and the road behind it, for example. The Sobel filter, developed by Irwin Sobel and Gary Feldman in 1968, finds those places by estimating how fast the image intensity is changing at every pixel. Where that rate of change is large, there is an edge; where the image is flat, there is not. It remains one of the most widely used edge detectors precisely because it is cheap to compute and maps very naturally onto hardware.

A Little Mathematics

Treat the grayscale image as a function I(x, y) giving the brightness at each pixel. The filter slides two small 3×3 kernels across the image — one sensitive to horizontal change, one to vertical:

Label the nine pixels of the neighbourhood a to i, reading left to right and top to bottom. The convolution then collapses into nothing more than a handful of additions and subtractions:

Gx = (c + 2f + i) − (a + 2d + g)

Gy = (g + 2h + i) − (a + 2b + c)

So Gx is a weighted difference between the right and left columns, which grows large across a vertical edge, and Gy does the same between the bottom and top rows. What makes the kernel well behaved is that it is separable — the outer product of a smoothing vector and a differencing vector:

[1, 2, 1]T × [−1, 0, +1]

The [1, 2, 1] half is a crude Gaussian blur that suppresses noise, and the [−1, 0, +1] half is a central-difference derivative. Blurring slightly perpendicular to the direction being differentiated is what makes Sobel noticeably more noise-tolerant than a naive two-point gradient.

The two gradients combine into a single edge strength. The textbook answer is the Euclidean magnitude, but a square root is expensive in FPGA logic — so this design uses the standard L1 approximation instead:

|G| = sqrt(Gx2 + Gy2)  ≈  |Gx| + |Gy|

It overestimates the true magnitude slightly, but it preserves relative edge strength perfectly well for detection — and it costs only adders, a two’s-complement negation and a multiplexer, instead of a square-root unit. That single substitution is the difference between a design that fits comfortably in a small FPGA and one that does not. A final stage then clamps the result back into the 8-bit range 0–255, and border pixels, which have no complete 3×3 neighbourhood, are forced to black to match the OpenCV reference behaviour.

Milestone 1 — Proving the Algorithm in Simulation

Before any of this could run on a board, the arithmetic had to be demonstrably correct. I wrote the Sobel engine as a parameterised Verilog module that accepts pixels as a continuous stream, holding the three most recent image rows in internal shift registers so that a full 3×3 neighbourhood is always available — much like keeping the last three lines of text in view while reading. A self-checking testbench feeds it a real photograph and captures the result.

The verification is the part I am most pleased with. Python converts the source image into a plain hex file, the Verilog simulation filters it, and Python then reads the result back and compares it pixel by pixel against OpenCV’s own Sobel output, reporting a match percentage and a visual difference map. That turns “it looks about right” into an objective, repeatable number. I also wrapped the entire flow — preprocess, compile, simulate, verify — into a Tkinter GUI that shows the input, the hardware output and the golden reference side by side, which made iterating far quicker than retyping command lines.

Milestone 2 — Real Hardware, Real Monitor

The second milestone turned the verified module into a complete self-contained system on a Basys3 Artix-7 board. Only one step still happens on a PC: a short Python script converts a photograph to grayscale, resizes it to 320×240 and writes it out as a memory-initialisation file. Everything after that is physical circuitry.

The design runs in two stages. On power-up, a controller streams the stored image out of on-chip block RAM, through the Sobel engine, and writes the filtered result into a second block RAM — the whole pass finishing in about 3 milliseconds. From then on, a hardware VGA controller generates standard 640×480 @ 60 Hz timing and continuously scans that result out to a monitor, duplicating each pixel into a 2×2 block so the smaller image fills the screen. A clock-management block derives the required 25 MHz pixel clock from the board’s 100 MHz oscillator. No software executes during either stage; the entire system is logic responding to a clock.

Three Bugs Only Real Hardware Would Show

Simulation passed cleanly, and the design still misbehaved on the bench. Three defects surfaced only once the output reached a physical monitor, and diagnosing each one against the known-good Milestone 1 reference image was the most instructive part of the project.

The first was a race against the clock: the clock-management block produces a LOCKED signal saying its 25 MHz output has stabilised, and I had generated that signal but never used it — so the design could start running on an unstable clock. The second showed up as part of the picture wrapping onto the opposite edge of the screen: during VGA blanking intervals the display logic was still computing a “next pixel” address, reading past the end of the image and fetching stale data. The third was the subtlest — a diagonal shear across the image, each row offset one pixel further than the one above it. The controller was performing one extra, uncounted memory read at the start of every row, and because block RAM returns data a full cycle after the address is presented, that offset accumulated row by row. Moving the extra read so it happens once at the very start, rather than repeatedly, straightened the image out.
